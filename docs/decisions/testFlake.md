# testFlake (wave 60, CFG-67 / CFG-77): the app suite's rare "Compose did not get idle" flake, and the page editor's hotspots link

## 1. The flake (CFG-67's `SettingsPolishW58PanesTest`)

Reported: `:app:testDebugUnitTest`'s three `SettingsPolishW58PanesTest` tests (`CFG_67_aThemesHitLightsItsRow`, `CFG_67_aDrawerShortcutsHitLightsThatSegmentOrTheReset`, `CFG_67_theRadarPanesLightTheirRows`) failed every time in the last two full-suite runs with `androidx.test.espresso.AppNotIdleException: Compose did not get idle after N attempts in 60 SECONDS`, but pass alone or with a handful of other classes.

### What was checked (in this worktree, `./gradlew :app:cleanTestDebugUnitTest :app:testDebugUnitTest --offline -q --max-workers=2` unless noted)

- **Reproduced.** Every full run in this investigation (seven, after the wave 59 merge) failed with this exact exception, always inside the back half of the alphabetically-run suite (roughly test 550-750 of 761).
- **Found the predecessor, twice, with a temporary instrumented run** (a Gradle `TestListener` added to `app/build.gradle.kts` behind a `-Pw60LogTestOrder` flag, logging `class#method` and the forked JVM's pid to a scratch file; removed again once used — never committed). The two runs gave two **different** predecessors in the same JVM fork: once a pure data test with no Compose rule at all (`SettingsPolishW58AppTest`), once an unrelated Crash Recovery test (`CrashRecoveryIntegrationTest`). The failing test itself also varied between runs (`SettingsPolishW58PanesTest` most often, but also `DefectsW58AppTest` and `ui.DockWiringTest` in two runs). **This rules out one specific leaked animation from one specific predecessor test** — the likely cause (c) in the brief, "the Hotspots editor's pulsing selection animation started in an earlier test and never disposed" — as the sole or even primary explanation: the predecessor is not reliably the same test, and is sometimes a test that renders no Compose UI whatsoever.
- **Found and fixed one real gap anyway.** Every other app and feature-grid test that composes the Hotspots editor (`HotspotsEditorW59UiTest`'s clock-driven tests, `GlanceTopW59SmokeTest`'s CFG_75/76 tests) either forces `ReducedMotionTesting.force(MotionPrefs(0f, 0f, 0f))` or drives the clock manually (`rule.mainClock.autoAdvance = false`) before composing it, because its selected corner pulses with a real `rememberInfiniteTransition`. `GlanceTopW59AppTest.CFG_77_inSettingsATapTogglesAndPersistsAndEditOpensTheCornerEditor` (the one test that opens Settings, scrolls to Corners and taps the live row) did not. Fixed to match the established pattern (`ReducedMotionTesting.force(...)` in the test, reset in `@After`). **This is a legitimate correctness fix, kept**, but a full run with only this fix applied still hit the exact same flake (on `SettingsPolishW58PanesTest` again) — so it was not, by itself, the root cause either.
- **Heap:** raised `test.maxHeapSize` from 2g to 3g (the exact lever wave 22's comment in this same file already used for "Compose never idle under GC pressure" once before, at a smaller suite size). No improvement; the same test failed on the next full run.
- **`forkEvery`:** tried restarting the test JVM every 250 tests (no improvement; still failed, in what would have been test ~200 of a *fresh* fork) and every 50 tests (markedly **worse**: 25 failures instead of 3-6, and the run took 29 minutes instead of 5-9 — the extra JVM-startup churn on this 4-CPU, shared host plausibly made things worse, not better).
- **`--max-workers=1`** (removes contention between this task's own two forks entirely): still failed, with yet another pair of victims (`SettingsPolishW58PanesTest` again, plus `ui.DockDialogsW24Test` and `ui.DockWiringTest` cascading after it).
- **Control run on an effectively unmodified checkout:** reverted `app/build.gradle.kts` and `GlanceTopW59AppTest.kt` to their committed (pre-wave-60) state, keeping the rest of this wave's unrelated production code (the page editor's hotspots link, which the failing test's code path never touches), and ran the full suite again. **It failed the same way**, on `SettingsPolishW58PanesTest`. This is the "fails on an unmodified checkout too" evidence the brief asked for: the flake predates this wave's work and is not caused by the Hotspots editor feature.
- **Ran `SettingsPolishW58PanesTest` alone** right after that control run (same host, same ambient load): passed in 8 seconds.
- The host is shared and resource-constrained (4 CPUs, 15 GB RAM; `ps` during the investigation showed other heavy Java processes and, once, another agent's `git worktree remove` in flight), which is consistent with a flake whose victim and predecessor both vary between otherwise-identical runs.

### Honest conclusion

This is a real, intermittent flake, reproducible only in the full `:app:testDebugUnitTest` run (761 tests in one or two long-lived Robolectric/Compose JVMs), not reproducible alone, and not eliminated by any single lever tried here (heap, `forkEvery`, worker count, or fixing the one real gap found). It is not possible to honestly claim it is fixed. The strongest supporting fact is that this exact failure signature ("Compose did not get idle ... under GC/resource pressure") already happened once before, at a smaller suite size, and was patched then by raising the heap (the surviving comment in `app/build.gradle.kts` above the (unchanged) `maxHeapSize = "2g"` line); this wave's net addition of tests (new Hotspots editor UI/smoke tests, more screenshot tests) most likely pushed the same class of bug back into range, but this time a bigger heap alone did not clear it, and the two process-churn levers tried (`forkEvery`) made things no better or actively worse. The fix applied (reduced motion in the one real gap found) is kept as a genuine improvement and matches the rest of the codebase's established pattern, but is not asserted to be the complete fix.

**Mitigation recommended, not applied here** (outside this wave's scope, and the brief asked for the exact result of the mandated run rather than a CI change): retry the `:app:testDebugUnitTest` task once on failure in CI, or split it into two or three `--tests` batches run as separate Gradle invocations (each a fresh JVM with a bounded test count), rather than tuning `forkEvery` inside one invocation (tried here, and made as a lever only shows improvement is not free: 50 made the problem worse).

### Regression test added anyway

`HotspotsEditorW59UiTest.CFG_77_wave60_disposingTheEditorCancelsItsPulseSoTheHostStaysIdle` (feature-grid): composes the Hotspots editor with real motion (not forced), lets its selected corner's pulse run a few real frames, then removes the editor from composition (a boolean swap, not a whole-rule teardown) and asserts `rule.waitForIdle()` returns promptly. This guards specifically against the shape of bug the brief suspected (an infinite transition that outlives its composition); it passes today, which is further evidence the investigated flake is not that specific shape, but it is a correctness guard worth keeping regardless.

## 2. The page editor's hotspots link (CFG-77, the "not done" item)

Wave 59 had already removed the per-corner toggles from the page editor's Settings tab (`glanceTop.md`'s list of what wave 59 removed names "the page editor's Settings tab hotspot switches"); what was missing was a way back into the one real editor. Added: a row "Edit hotspots" (style and tag matching the tab's other action tiles — `ActionTile`, now given an optional right-aligned summary and test tag), under a small "Hotspots" heading, in the Glance block of `SettingsContent` (`PageEditorTabs.kt`), reading the same "N of 4 on" summary the Settings and Home-sheet rows use. Wired through `PageEditorSettingsActions.onEditHotspots` → `PageEditorHost`'s new `onEditHotspots` parameter → `EditCardOverlay`'s new parameter → `HomeScreen.kt`'s existing `hotspotsPage` state (the same boolean the Home sheet's tile already sets), so tapping it opens the exact same `HotspotsEditorPage` instance as Settings > Home > Corners and the Home sheet tile, reading and writing the same `glanceHotspots` preference. No new per-corner toggles were added back (there were none left in this tab to remove — wave 59 had already taken them out), so the owner's "keep only the newest option" policy needed no further action here.

Tests: `PageEditorUiTest.HOM_12_pe51_editHotspotsRowOpensTheEditor` (row displayed, tap calls the callback), `HOM_12_pe51b_editHotspotsRowIsGoneWithNoCallerWired` (no row, no stray "Hotspots" heading, when the caller passes none — keeps `HOM_12_pe24b`'s existing "the old per-corner switches are gone" assertion true), `PageEditorAppTest.HOM_12_pe52_editHotspotsOpensTheEditorAndAnEditThereReflectsOnTheRow` (real app: opens the page editor, focuses Glance, taps the row, the Hotspots page opens, toggling a corner there updates the stored preference, dismissing returns to the page editor whose row summary now reads "3 of 4 on" — the same store, so the change is visible without any extra wiring). Screenshot `feature-grid/build/screenshots/page_editor_glance_focus_edit_hotspots.png` (read: the row sits under a small "Hotspots" heading below "Show music", same rounded-tile style as the Folders tab's action tiles, "4 of 4 on" right-aligned; nothing needed fixing).

Hotspots link: revert the `onEditHotspots` parameter threaded through `PageEditorTabs.kt` / `PageEditorHost.kt` / `EditCardWiring.kt` / `HomeScreen.kt` and the "Edit hotspots" row in `SettingsContent`; the tab returns to only "Show music" under Glance.
