# w18-crashRecovery: status

Stream: wire the owner's shared crash-recovery utility (`mbaliga/Shared-Libraries-asoc`, `:crash-recovery` 1.4.0) in front of safe mode, remove our duplicate, and hunt for a real startup crash from state older builds wrote. Decisions: `docs/decisions/crashRecovery.md` (sequence, handler order, resets) and `docs/decisions/startupCrashes.md` (the hunt and the answer). Nothing here has been confirmed on a device: see `docs/device-checklist.md`, section "Crash recovery screen and startup crashes (wave 18)". Screenshots of the safe mode screen with the new button (portrait dark, landscape light): `feature-grid/build/screenshots/cfg09-safemode-viewreport-dark.png` and `cfg09-safemode-viewreport-land-light.png`.

## Answer to the owner's two questions

1. "Not wired in the crash recovery utility?" Correct, it never was. Earlier waves wrote a local copy with no splash, no readable report and no share. It is now vendored as module `:crash-recovery` (Shared-Libraries-asoc `d4ade55`, byte for byte, own `build.gradle.kts` with a header, tests running in our build) and wired as the library documents: `install` is the first statement of `Application.onCreate`, `captureExitDeath` runs at start for native crashes and ANRs, `maybeShowRecovery` is the first statement of `MainActivity.onCreate`. The local report format, `CrashShare` and the report list are deleted.
2. "The two startup crashes": **no startup crash from old persisted state was reproduced.** The likely cause is not a crash: the loop guard counts starts that did not stay up 30 seconds, so two quick restarts (an install over the running launcher, twice) give safe mode with no exception anywhere (reproduced by a test). The one real crash class found (a preference key holding the wrong type throws `ClassCastException` out of the stores' constructors, on every start) is fixed, but the history shows no earlier build wrote such a key. Evidence and limits: `docs/decisions/startupCrashes.md`.

## Residue

* No device run. The native-crash and ANR path, the real share sheet and file picker, the Lab row on a phone, and an install over the owner's build are checklist rows.
* The owner's two crashes: not reproduced as crashes (see above). The guard still counts starts and not crashes; making it count crashes changes CFG-09 and needs the owner's decision (recommendation in `startupCrashes.md`).
* The host works around two points of the vendored library instead of editing it (the double report for one JVM crash, and `super.onCreate` before the early return). Both should be fixed upstream in Shared-Libraries-asoc; then `CrashRecoveryHost.markExitHistorySeen` can go. The library's private file names are relied on and pinned by a test.
* The library's `maybeShowRecovery` and `captureExitDeath` read a few small files on the main thread at start (their documented contract).
* The share tiles of the library are Copy, Save file, Email and WhatsApp; the generic share sheet is what Email opens (and the fallback of the others). There is no separate "Share" tile.
