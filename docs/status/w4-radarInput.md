# Wave 4 Radar nesting and input gaps (PAL-03, PAL-08, INP-01, INP-05, INP-07, INP-11, INP-20)

Nothing here is device-verified. "built" means the code is wired into the live screens and covered by JVM or Robolectric tests; "partial" names the exact step that is left.

| PAL-03 | partial | Code gap closed: an app's own launcher shortcuts that match the query are nested inside the app's tile or row in all three Radar layouts instead of separate rows (`NestedShortcuts`, `Tile.App.shortcuts`, `SearchData`). Filmstrip and Orbit draw up to two pills under the tile plus a "+N" pill that opens the preview, which lists every shortcut; Flat draws all of them in a sideways row inside the app's row. They are reachable by keyboard too: the app's action list (Tab or Right) lists them right after "Open" (`ResultMenuEntry.shortcut`). Rules, stated: a shortcut whose app did not match the query (it matched on its own label) has no tile to sit in and stays an Actions row; at most 4 per app are nested and the rest stay Actions rows so none is lost; with two profile copies of a package the first (best) tile carries them. Tests: `RadarNestingTest` (data rules, keyboard list, Filmstrip, Orbit and Flat rendered and tapped). Still open, device only: shortcuts are listed only while Liftoff holds the default-home role (a platform rule), so the run as the default home on a phone is the last step. |
| PAL-08 | partial | Code gap closed: "Open on display" with several displays and "Add to workspace" now run from Radar's own list through a small chooser dialog (`RadarChoicePicker`, state `RadarPickerState`) instead of the home's app sheet. Still open, device only: no device with a second display was available, so "Open on display" has never run with real displays; the chooser dialog itself is not rendered by a test here. |
| INP-01 | partial | Code gaps closed: (1) the dock rail is on the shared focus graph: every pinned and recent item, the workspace chip, the About and panel buttons and the enable row register as `FocusNode`s through `DockInput.FocusBridge` (installed by `DockInputWiring` in the app, since the dock module cannot see the grid module), so arrows leave the rail into the home and back and the graph knows what has focus; the desktop surface's rail passes no bridge so it stays out of the phone home's graph. Launchpad's rows are deliberately not graph nodes: STR-08 owns its up and down, Home and End, left and right to collapse or expand, and Esc, and a geometry graph would swallow Left and Right. Tests: `W4RadarInputDockTest` (rail nodes registered, focus reported, a removed pin leaves the graph, a bridge-less rail stays off), `InputTouchPathsUiTest` (Launchpad layer blocks arrows and Tab). ## Adversarial review (final)

Re-read the whole diff against the Spec rules. No hidden API, reflection, accessibility service, permission or model-name check was added; no new animation, SharedPreferences file or main-thread I/O (the drop and pin edits go through the existing stores), so the NFR audit tests stay as they were. Things that would have been silent simplifications and were not: the strings new to `L10n.tr` all have eight languages; shortcuts beyond the cap and orphan shortcuts are kept as rows; the pin-list fallback for number keys is stated as not counting Recent; INP-01 says which controls are not on the graph and why Launchpad's rows are not. One test-order bug found and fixed in my own tests (another test switched the UI language, so labels are looked up after setting English). Statuses above are the honest final table.
