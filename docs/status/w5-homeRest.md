# Widgets, stacks, files tile and reconcile residue, wave 5 (stream "homeRest"): status

Status vocabulary as in earlier waves: built = compiles and is covered by JVM or Robolectric tests; partial = some of it is built or wired and a device or owner step remains. Nothing here is device-confirmed.

New code: `core-catalog` `MemberReconcile.kt`, `FileThumbs.kt` (and a fix in `HomeRekey`); `feature-desktop` `WidgetResizeHandle.kt` and resize rules in `DesktopWidgets.kt`; `feature-grid` swipe strips in `WidgetStackView.kt`, Files tile cells in `HomeExtrasUi.kt`, unavailable cells in `FolderUi.kt`; `feature-dock` widget grip in `DockRail.kt`; `app` `HomeItems.reconcileMembers`, `refreshFiles`, `DesktopWidgetProvider.resizeLimits`; `core-design` `L10nW5homeRest.kt`. Tests: `MemberReconcileTest`, `FileThumbsTest`, `HomeRestW5Test` (core-catalog), `DesktopWidgetResizeTest`, `DesktopWidgetResizeUiTest` (feature-desktop), `WidgetStackViewTest` (more cases), `FilesTileUiTest` (feature-grid), `DockWidgetSlotUiTest` (feature-dock), `HomeRestW5AuditTest` (core-quality). No test was deleted or loosened.

| HOM-13 | partial | Closed here: a placed desktop widget can be resized. The widget has a corner handle (`WidgetResizeHandle`, drag; live preview; commit on release) and a size menu ("Wider", "Narrower", "Taller", "Shorter", one cell each) in its long-press menu. Rules in `DesktopWidgets.resizedRect/resize/resizeByCells`: the top-left corner stays, the size snaps to whole cells, at least one cell, inside the work area, never over another widget (when the wanted size would overlap or leave the area the largest size that does not is used), and the provider's own limits apply (`ResizeLimits` from `resizeMode`, `minResizeWidth/Height`, read by `DesktopWidgetProvider`; a provider that cannot be resized gets no handle and no menu entries). The new size is committed to the per-display profile (round trip through `ProfileCodec` tested) and the hosted view is told its new size by `HostedWidget`. Tests `HOM_13_*` in `DesktopWidgetResizeTest` (logic) and `DesktopWidgetResizeUiTest` (Robolectric: handle drag grows the widget, drag toward a neighbour stops before it, a non-resizable provider has no handle, the size menu widens). Needs a device: the proof on a second display (a hosted widget renders, updates and takes touches there), and that real providers' `resizeMode` and minimum resize sizes give sensible limits. |
| HOM-14 | partial | Closed here: the swipe is now proven with injected pointer input (`WidgetStackViewTest`): swipe up and left go forward, down and right go back, a drag shorter than 48 dp does nothing, the stack wraps at both ends. Hosted-widget touch passthrough is as robust as the public API allows: a hosted view takes every touch that starts on it and the API has no way to take a drag back from it, so the stack draws two overlay strips above the widget that are always the stack's own, a bottom strip (28 dp, carries the dots) and one along the trailing edge; tests run a child that consumes all drags and show the strips still switch while a drag in the middle belongs to the widget (also asserted, as the limit). A one-widget stack has no strips. The active member is kept per stack, and a stack is one slot of one page: its active index lives in its own definition, so two stacks on different pages never share it and it survives moving the stack to another page and the state codec (`HOM_14_eachStackPositionKeepsItsOwnActiveMemberAcrossPages`, `..._survivesMovingTheStackToAnotherPageAndAReload`). Note: the spec text for HOM-14 says only "switched by swipe, scroll wheel or keys"; no per-page-position rule is written there, so this is the reading used. Needs a device: that a real `AppWidgetHostView` lets the strips and the rest of the stack work together (the menu entry "Next widget in stack" and the keys remain the alternatives). |
| HOM-10 | partial | Closed here: the reconcile step for folders and the dock (`MemberReconcile`, wired from `HomeScreen` through `HomeItems.reconcileMembers`). An app that a folder or the dock refers to and that is missing from the full inventory (hidden apps included) is unavailable first: its cell is kept, and the folder sheet draws it dimmed as "App unavailable" with a "Remove" action. After a grace period of 7 days (`MemberReconcile.GRACE_MS`) it is removed through `HomeEdit.pruneMissing`: no gap, a folder left with one app dissolves, an empty folder goes, a missing dock pin goes. A package that comes back inside the period keeps its place; an empty inventory (not loaded yet) changes nothing; pages are not judged by this step (the page resolver already drops missing keys). The first-seen-missing times are kept in the existing `liftoff_misc` preference (excluded from backup). Archived and suspended apps stay in the inventory and are shown dimmed by the existing app presentation, so they are never removed here. Tests `HOM_10_*` in `MemberReconcileTest`. Owner decision: the spec gives no grace period, 7 days is a choice (long enough for a locked work profile or a reinstall). Not done: the dock rail still omits an unavailable pin until the grace ends instead of drawing it dimmed (the rail resolves labels from the live app list in `feature-dock`, outside this stream's files). Needs a device: that Android 15 builds keep archived apps in `LauncherApps.getActivityList` with `FLAG_INSTALLED` clear, and the 1 second figure measured with a real install, update, uninstall, disable, archive and suspend. |
| HOM-15 | partial | Closed here: the Files tile shows live thumbnails of the first four files (`FileThumbs`, `ContentResolver.loadThumbnail` on the file's document URI, which carries the folder grant; no storage permission and no MediaStore). Tests `HOM_15_*` in `FileThumbsTest` (bounds, cache, fallback, at most four asked) and `FilesTileUiTest` (Robolectric: names, thumbnail with accessible name, plain glyph, only four cells, the platform call yields null for an unknown provider), audit `HomeRestW5AuditTest`. Needs a device: the system folder picker, opening real files, and that real providers return thumbnails for the tile cells. |
